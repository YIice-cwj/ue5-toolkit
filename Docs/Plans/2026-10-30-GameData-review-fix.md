# [L3 任务计划]：GameData 审查缺陷根因修复

> **关联准则**：B2 计划先行、B3 最小变更、B4 必要防御、B5 深度验证、B7 根因溯源、B-CMT 注释同步
> **任务等级**：L3 复杂缺陷修复
> **状态**：已批准（APPROVED）

---

## 1. 背景与核心目标

### 现状与问题

GameData 审查确认以下缺陷与契约失配：

1. 槽位删除会清除已签发保存代次；删除后新保存从低代次重新计数，旧异步写可通过过期检查并覆盖新档，形成 ABA 竞争。
2. 同槽位异步加载没有时序约束，旧续体可能在新请求之后应用；删除槽位也不会使已读取的在途加载失效。
3. JSON 加载在文件缺失、读取失败、解析失败时提前返回，预填充的输出表未按公开契约清空。
4. 槽位删除把任一文件删除成功视为整体成功；临时档恢复忽略原子换入失败。
5. 异步保存线程职责、二进制解析读取器位置、空仓库摘要等文档与实现不一致，部分测试辅助函数缺少规范要求的 Doxygen 文档头。
6. 现有同步测试真实有效，但未覆盖上述竞争与失败边界。

### 目标与产出

- 保证同一槽位的保存代次在删除前后严格单调，旧异步写永远不能覆盖删除后的新档。
- 同槽位异步加载采用“最新请求优先”：仅最新请求可应用，过期请求不调用业务 Load 并广播失败表示取消；删除使在途加载失效。
- 统一 JSON 与文件 I/O 的成功、失败语义，消除静默部分成功。
- 保持现有公开函数签名、存档格式和空摘要运行时行为不变，同步全部相关文档。
- 增加确定性回归测试；异步测试由真实完成回调驱动，不使用 sleep、概率性压测或私有状态绕行。

### 非目标

- 不引入统一槽位操作协调器，不重写存档子系统或异步任务执行器。
- 不改变公开函数签名、Blueprint 调用方式、`.sav` / `.bin` 格式或段迁移协议。
- 不处理审查范围外的 GameDataSamples、GameCore 或其他插件问题。
- 不整理无关代码、不大面积格式化，不覆盖工作区已有修改，不执行 Git commit 或 push。

## 2. 方案对比决策矩阵

| 维度 | 方案 A：定向根因修复（推荐） | 方案 B：统一槽位协调器 | 方案 C：仅修 BLOCKER |
|---|---|---|---|
| 核心机制 | 保存与加载分别维护单调代次，局部修正 I/O 和输出契约 | 新组件统一管理保存、加载、删除状态 | 仅修保存 ABA、JSON 和注释 |
| 优势 | 根治问题、公开 API 稳定、爆炸半径小 | 状态集中，后续扩展统一 | 改动量最小 |
| 劣势 | 保存与加载代次由各自所有者维护 | 重构范围和回归面明显扩大 | 遗留异步加载与 I/O 缺陷 |
| 爆炸半径 | GameDataCore 存档、静态数据工具及对应测试/文档 | 整个存档调用链和潜在外部调用方 | 同方案 A 的部分文件 |
| 迁移成本 | 无签名或格式迁移 | 需要内部调用迁移和更完整并发验证 | 无，但修复不完整 |

**选型结论：** 采用方案 A。保存代次的所有者仍是 `FSaveGameFileIO`，加载代次由 `USaveGameSubsystem` 在主线程维护，职责边界保持清晰；无需为一次缺陷修复增加新的架构层。

## 3. 实施步骤

### Step 1：建立失败回归基线

- 为“旧保存代次 → 删除 → 新保存代次 → 新档落盘 → 旧写放行”建立确定性文件 I/O 测试，直接断言新代次严格增大且最终字节属于新档。
- 通过公共异步加载 API 连续发起同槽位请求，以自动化 latent command 等待真实完成回调，断言仅最新请求调用业务 Load，回调包含一次取消和一次成功。
- 增加 JSON 文件缺失、读取/解析前置失败时输出表清空的测试，以及空仓库 SHA-1 契约测试。
- **验证门禁：** 新测试可编译；缺陷回归测试在修复前稳定暴露对应问题，契约型测试与既有测试基线记录完整。

### Step 2：修复保存与加载时序

- 删除槽位时保留已签发保存计数；清除删除墓碑后，新保存继续使用严格递增的下一值。
- 为每槽位异步加载签发主线程代次，续体仅在代次仍为最新时反序列化并应用；过期请求广播 `false`，不得触碰业务段。
- 删除槽位使在途加载代次失效；子系统销毁时清空加载代次表。
- **验证门禁：** 保存 ABA 与最新加载优先测试通过，既有同步存档测试无回归。

### Step 3：统一 JSON 与文件 I/O 失败契约

- JSON 输出表在入口清空，后续沿用局部错误统计与行级回滚逻辑。
- 删除操作仍尝试清理正式档和临时档，但只有发现文件且所有必要删除均成功才返回 `true`；无文件仍返回 `false`。
- 临时档恢复检查原子换入结果，换入失败记录错误并返回 `false`。
- **验证门禁：** JSON 前置失败测试、临时档正常恢复测试和全部既有存档测试通过。

### Step 4：同步注释、API 文档与测试文档头

- 异步保存文档改为主线程段捕获/序列化、后台仅负责文件写入。
- 二进制表解析文档改为读取器已消费 Magic 和版本、定位到表数量字段。
- 空仓库摘要文档统一为 SHA-1 空输入摘要，保留现有运行行为。
- 补齐触及测试中辅助函数的多行分标签 Doxygen 文档头，并同步新函数、新行为的参数与返回值说明。
- **验证门禁：** 文档描述与实现逐项一致，无业务行内注释或单行压缩 Doxygen。

### Step 5：全量验证与差异审计

- 编译 GameDataCore 及依赖目标，运行 `Game.Data` 全量自动化测试。
- 对照审查清单复验保存、加载、JSON、I/O、空摘要和注释六项问题。
- 检查最终差异仅包含本计划文件，确认未混入工作区其他修改。
- **验证门禁：** 编译成功、所有测试通过、无 sleep 盲等、无未经授权提交。

## 4. 风险研判与应急回滚预案

### 潜在风险

- 过期加载以 `false` 回调表示取消，需要日志和 API 文档明确，避免被误判为磁盘损坏。
- 加载代次只能在主线程读写，不得把 UObject 或段注册表访问扩展到后台线程。
- 删除返回语义从“任一成功”收紧为“全部成功”，可能暴露过去被静默忽略的文件系统故障，这是预期的契约纠偏。
- 异步 latent 测试必须以回调完成为退出条件，不能用固定延时掩盖任务未执行。

### 回滚路径

1. 若验证出现致命回归，按本次差异块逆向恢复对应实现与测试，保留工作区原有修改。
2. 优先恢复公开行为兼容部分，再恢复内部代次逻辑；不使用破坏性 Git 命令清理其他文件。
3. 重新编译并运行既有 `Game.Data` 基线，确认回滚未扩大影响。

### 客观验收指标

- 保存 ABA 回归在旧实现稳定失败、在新实现通过，最终文件内容明确属于新档。
- 连续异步加载只应用一次业务 Load，回调结果严格为一次取消、一次成功。
- JSON 三类前置失败均清空预填充输出表。
- 空仓库摘要与文档声明的 SHA-1 空输入值一致。
- GameDataCore 编译成功，`Game.Data` 全量用例通过，无新增测试失败。
